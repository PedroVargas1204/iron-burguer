Conceitos

O que é um padrão de projeto

Um padrão descreve uma solução para um problema que ocorre com frequência no desenvolvimento de software: um par problema/solução que pode ser reaplicado em contextos diferentes.

Não é código pronto

Não é classe nem biblioteca para plugar no sistema: é um modelo, uma receita de como organizar classes e objetos.

Origem: GoF

Catálogo de 23 padrões de Gamma, Helm, Johnson e Vlissides, a Gang of Four, reunidos a partir de soluções testadas na indústria.

Por que usar

Reuso, manutenção mais fácil, vocabulário comum na equipe e flexibilidade para mudanças.

Elementos da descrição GoF: nome, problema, solução, estrutura, colaborações e consequências. Neste trabalho, cada padrão é apresentado por objetivo, contexto, problema e solução, seguido de um exemplo.

Categoria 1 · Criacionais

Padrões criacionais

Lidam com a criação de objetos: abstraem o processo de instanciação e controlam como os objetos são criados, aumentando a flexibilidade e o reuso. O código que usa um objeto deixa de depender da classe concreta que o cria.

Prototype

Especifica os tipos de objetos a criar usando uma instância protótipo e cria novos objetos copiando esse protótipo.

No Iron Burguer: cadastrar um produto a partir de outro (UC01).

Singleton

Garante que uma classe tenha uma única instância e fornece um ponto de acesso global a ela.

No Iron Burguer: a fila de produção única (UC12 e UC13).

Outros padrões da categoria: Abstract Factory · Builder · Factory Method

Criacional · escopo de objeto

Prototype

Objetivo

Criar novos objetos copiando uma instância já configurada, o protótipo, em vez de construí-los do zero.

Contexto

Objetos que diferem pouco entre si e têm configuração trabalhosa, ou classes que só são conhecidas na execução.

Problema

Para criar um objeto parecido com outro, o cliente precisa conhecer a classe concreta e repetir toda a configuração, inclusive a dos objetos contidos nele.

Solução

Declarar clonar() em uma interface comum. Cada classe concreta sabe copiar a si mesma; o cliente pede o clone e ajusta só o que muda.

Participantes: Prototype, a interface com clonar() · ConcretePrototype, que implementa a cópia · Client, que pede o clone ao protótipo

Exemplo · proposta para o UC01 Cadastrar Produto

Prototype no Iron Burguer

Todo produto tem preço e ficha técnica com ingredientes e quantidades (RNG02). Os hambúrgueres de peixe, frango e boi (RNG01) têm fichas parecidas: o novo nasce do clone de um já cadastrado.

O protótipo se copia

class Hamburguer extends Produto
        implements Prototipo<Hamburguer> {
    private TipoCarne tipoCarne;
    private List<FichaTecnica> ficha;
    public Hamburguer clonar() {
        Hamburguer copia =
            new Hamburguer(nome, preco, tipoCarne);
        for (FichaTecnica f : ficha)
            copia.ficha.add(f.clonar());
        return copia;
    }
}

O Gerente parte do clone

// UC01: incluir a partir de um existente
Hamburguer frango = boi.clonar();
frango.setNome("Hambúrguer de frango");
frango.setTipoCarne(TipoCarne.FRANGO);
frango.trocarIngrediente(carneBoi,
                         carneFrango);
controladorProduto.incluir(frango);
// grava e exibe MSG01

Ganho: o produto novo parte de uma ficha técnica completa, e o Gerente troca só o que muda. Cuidado: a cópia tem de ser profunda; com a ficha compartilhada, trocar a carne do frango mudaria a do boi.

Criacional · escopo de objeto

Singleton

Objetivo

Garantir que uma classe tenha uma única instância e fornecer um ponto global de acesso a ela.

Contexto

Recursos que precisam ser únicos e são usados por várias partes do sistema: uma fila, um contador, uma configuração.

Problema

Nada impede que cada parte do sistema crie a sua instância com new. As cópias divergem, e uma variável global não impede novas instâncias.

Solução

A classe controla a própria instância: construtor privado, atributo estático e getInstancia(), que cria o objeto na primeira chamada e depois devolve sempre o mesmo.

Participantes: Singleton, que guarda a instância e oferece getInstancia() · Clientes, que obtêm a instância e nunca a criam

Exemplo · UC12 Registrar Pagamento e UC13 Controlar Fila de Produção

Singleton no Iron Burguer

O pedido só entra na fila após a confirmação do pagamento (RNG20) e é produzido nessa ordem (RNG23).

A classe controla a instância

public final class FilaProducao {
    private static FilaProducao instancia;
    private final List<Pedido> fila = new ArrayList<>();

    private FilaProducao() { }

    public static synchronized
            FilaProducao getInstancia() {
        if (instancia == null)
            instancia = new FilaProducao();
        return instancia;
    }
}

Quem usa não cria

// UC12: pagamento confirmado (RNG20)
FilaProducao.getInstancia()
    .enfileirar(pedido);

// UC13: tela da Produção
List<Pedido> fila =
    FilaProducao.getInstancia()
        .listarFila();
if (fila.isEmpty())
    exibir(MSG22);

Ganho: o Cliente e a Produção enxergam a mesma fila, na ordem do pagamento, o que ataca o P8, a fila não respeitada. Cuidado: estado global dificulta testes, e acessos simultâneos exigem sincronização.

Categoria 2 · Comportamentais

Padrões comportamentais

Focam nos algoritmos e na atribuição de responsabilidades entre os objetos, descrevendo como eles interagem e distribuem responsabilidades durante a execução.

Command

Encapsula uma solicitação como um objeto, permitindo parametrizar clientes, enfileirar ou registrar solicitações e desfazer operações.

No Iron Burguer: a baixa de estoque desfeita no cancelamento (UC17 e UC18).

State

Permite que um objeto altere o seu comportamento quando o seu estado interno muda. O objeto parecerá ter mudado de classe.

No Iron Burguer: as situações do pedido (UC11, UC14 e UC15).

Outros padrões da categoria: Chain of Responsibility · Interpreter · Iterator · Mediator · Memento · Observer · Strategy · Template Method · Visitor

Comportamental · escopo de objeto

Command

Objetivo

Encapsular uma solicitação como um objeto, que pode ser enfileirado, registrado e desfeito.

Contexto

Operações que precisam ser guardadas para depois: executadas em fila, registradas em histórico ou desfeitas.

Problema

Quem solicita chama o executor diretamente. A operação termina na chamada: não sobra nada para enfileirar, registrar ou desfazer.

Solução

Uma interface com executar() e desfazer(). Cada comando guarda o receptor e os dados de que precisa; um invocador executa e mantém o histórico.

Participantes: Command · ConcreteCommand · Receiver, que faz o trabalho · Invoker, que executa e guarda · Client, que cria o comando

Exemplo · UC17 Baixar Estoque de Ingredientes e UC18 Repor Estoque de Ingredientes

Command no Iron Burguer

No pagamento, os ingredientes são baixados pela ficha técnica (UC12 inclui UC17, RNG28). Se um pedido pago for cancelado, eles voltam ao estoque (UC18 estende UC11, RNG22).

A baixa vira um objeto

class BaixarEstoque implements Comando {
    private final Map<Ingrediente, Double> consumo;
    BaixarEstoque(Pedido pedido) {
        consumo = pedido.consumoPelaFicha();
    }
    public void executar() {         // RNG28
        consumo.forEach(Ingrediente::baixarEstoque);
    }
    public void desfazer() {         // RNG22
        consumo.forEach(Ingrediente::reporEstoque);
    }
}

O invocador guarda o histórico

// UC12: pagamento confirmado
Comando c = new BaixarEstoque(pedido);
c.executar();
historico.put(pedido, c);

// UC11: cancela pedido pago (UC18)
historico.remove(pedido).desfazer();

Ganho: o comando guarda o que foi baixado, e a reposição devolve as mesmas quantidades. Cuidado: só se desfaz o que a regra permite; sem reembolso (RNG21), o pagamento não tem desfazer().

Comportamental · escopo de objeto

State

Objetivo

Permitir que um objeto altere o seu comportamento quando o seu estado interno muda. Ele parecerá ter mudado de classe.

Contexto

Objetos com ciclo de vida em estados, em que cada operação é permitida ou não conforme o estado atual.

Problema

Condicionais por estado repetidas em cada operação. A regra fica espalhada, e esquecer um caso gera um comportamento inválido.

Solução

Cada estado vira uma classe. O objeto delega a operação ao estado atual, e o estado define para qual outro ele passa.

Participantes: Context, o objeto que muda de estado · State, a interface comum · ConcreteState, uma classe para cada estado

Exemplo · UC11, UC14 e UC15: cancelar, atualizar a situação e entregar o pedido

State no Iron Burguer

Sem o padrão

void entregar() {
    if (situacao == PRONTO)
        situacao = ENTREGUE;
    else if (situacao == ENTREGUE)
        erro(MSG24);
    else
        erro(MSG16);
}
// e o mesmo if em cancelar(),
// iniciarProducao(), concluir()...

Com o padrão: o pedido delega

abstract class Situacao {          // padrão: recusa
    void cancelar(Pedido p) { p.erro(MSG16); }
    void entregar(Pedido p) { p.erro(MSG16); }
}
class Pronto extends Situacao {
    void entregar(Pedido p) { p.mudarPara(new Entregue()); }
}
class Entregue extends Situacao {
    void entregar(Pedido p) { p.erro(MSG24); }   // RNG26
}

Ganho: cada regra fica em um só lugar: só Pronto entrega (RNG25), e Entregue recusa a segunda entrega (RNG26). Custo: uma classe por situação no lugar da enumeração SituacaoPedido.
