O que é um padrão de projeto

Uma solução geral e reutilizável para um problema recorrente de projeto de software, dentro de um contexto determinado. Não é código pronto: é a descrição de como organizar classes e objetos para resolver aquele problema.

Origem

Catálogo publicado em 1994 por Gamma, Helm, Johnson e Vlissides — a Gang of Four (GoF), com 23 padrões consagrados.

Para que servem

Reduzir acoplamento, aumentar a coesão e permitir que o sistema evolua sem reescrever o que já funciona.

Vocabulário comum

Dizer “aqui usamos um Observer” comunica uma estrutura inteira à equipe em duas palavras.

Todo padrão é descrito por quatro elementos essenciais: nome, problema (quando aplicar), solução (classes, objetos e relações) e consequências (vantagens e custos).

As três categorias do catálogo GoF

Criacionais

Criação dos objetos

Abstraem como os objetos são instanciados, compostos e representados, separando o uso do objeto da decisão sobre qual classe concreta criar.

Abstract Factory · Builder · Factory Method · Prototype · Singleton

Estruturais

Composição dos objetos

Tratam de como classes e objetos se combinam para formar estruturas maiores, mantendo-as flexíveis e eficientes.

Adapter · Bridge · Composite · Decorator · Façade · Flyweight · Proxy

Comportamentais

Responsabilidades entre objetos

Tratam da atribuição de responsabilidades e dos algoritmos, descrevendo como os objetos se comunicam e cooperam.

Chain of Responsibility · Command · Interpreter · Iterator · Mediator · Memento · Observer · State · Strategy · Template Method · Visitor

O catálogo também classifica os padrões por escopo: os de classe resolvem o problema por herança, definida em tempo de compilação (Factory Method, Adapter, Template Method, Interpreter); os de objeto resolvem por composição, que pode mudar em tempo de execução (todos os demais).

Criacional · escopo de objeto

Prototype

Objetivo

Especificar os objetos a serem criados usando uma instância prototípica e criar novos objetos copiando esse protótipo.

Contexto no Iron Burguer

O cardápio sugere lanches prontos de carne, batata e bebida — 12 combinações possíveis (3 × 2 × 2, RNG01) — e no UC08 o próprio cliente registra dezenas deles por hora pelo aplicativo.

Problema

Montar cada pedido item por item, do zero, é lento no aplicativo e repete a mesma configuração o dia inteiro. Criar uma classe para cada uma das 12 combinações multiplicaria as classes sem necessidade.

Solução

Cada lanche sugerido é cadastrado uma vez como protótipo. Ao registrar o pedido, o sistema clona o protótipo e o cliente ajusta apenas o que quer diferente.

Design Patterns · Iron Burguer · 6 de 15

Prototype no Iron Burguer

O clone profundo

interface Prototipo {
  Pedido clonar();
}

class Pedido
    implements Prototipo {

  public Pedido clonar() {
    Pedido copia = new Pedido();
    for (ItemPedido i : itens)
      copia.add(i.clonar());
    return copia;
  }
}

O cardápio de protótipos

class CardapioDeLanches {
  private Map<String, Pedido>
      protos = new HashMap<>();

  void registrar(String nome,
               Pedido p) {
    protos.put(nome, p);
  }

  Pedido novo(String nome) {
    return protos.get(nome)
              .clonar();
  }
}

O uso no aplicativo

// UC08 - Registrar Pedido
Pedido p = cardapio
    .novo("LANCHE BOI");

p.trocarBebida(sucoLaranja);
p.observacao("sem cebola");

// o protótipo no cardápio
// continua intacto

Ganho

Um lanche novo no cardápio é cadastro, não código: o protótipo é registrado em tempo de execução.

Cuidado

Uma cópia rasa compartilharia a lista de itens — alterar o clone mudaria o lanche do cardápio. O clone precisa ser profundo.

Criacional · escopo de objeto

Singleton

Objetivo

Garantir que uma classe tenha uma única instância e fornecer um ponto global de acesso a ela.

Contexto no Iron Burguer

A fila de produção do dia é uma só, e a senha do pedido é um número sequencial único gerado pelo sistema (RNG14 e RNG23).

Problema

Se o aplicativo do cliente e a tela da cozinha criarem cada uma a sua fila, surgem duas verdades sobre a mesma operação: senhas repetidas e ordem de produção divergente — exatamente a falha que o cliente relatou.

Solução

A própria classe controla sua instância: construtor privado, atributo estático e um método getInstancia() que cria na primeira chamada e devolve sempre o mesmo objeto.

Design Patterns · Iron Burguer · 8 de 15

Singleton no Iron Burguer

A classe controla sua instância

public class FilaDeProducao {
  private static FilaDeProducao instancia;
  private List<Pedido> fila = ...;
  private int ultimaSenha = 0;

  private FilaDeProducao() { }

  public static synchronized
      FilaDeProducao getInstancia() {
    if (instancia == null)
      instancia = new FilaDeProducao();
    return instancia;
  }
}

Quem usa não cria

// app do cliente (UC12)
FilaDeProducao.getInstancia()
  .enfileirar(pedido);

// tela da cozinha (UC13)
Pedido p = FilaDeProducao
  .getInstancia().proximo();

// a mesma fila, a mesma ordem,
// a mesma numeração de senha

Ganho

Uma única fila e uma única sequência de senhas em todo o sistema, garantindo a ordem de chegada (RNG23).

Cuidados

Estado global dificulta testes e, com vários acessos simultâneos, exige controle de concorrência — por isso o synchronized.

Design Patterns · Iron Burguer · 10 de 15

Comportamental · escopo de objeto

Command

Objetivo

Encapsular uma requisição como um objeto, permitindo enfileirar requisições, registrá-las em log e apoiar a operação de desfazer.

Contexto no Iron Burguer

No UC13 os pedidos pagos entram numa fila de produção; no UC11 o cliente pode cancelar; e o gerente precisa do histórico para os relatórios (UC24 e UC25).

Problema

Se a tela chamar direto os métodos da produção, quem pede fica acoplado a quem executa. Não há como enfileirar, desfazer nem registrar o que foi solicitado.

Solução

Cada operação sobre o pedido vira um objeto com executar() e desfazer(). A fila guarda comandos, não chamadas, e o histórico de comandos é o log que alimenta os relatórios.

Design Patterns · Iron Burguer · 11 de 15

Command no Iron Burguer

A ação vira objeto

interface Comando {
  void executar();
  void desfazer();
}

class EnviarParaProducao
    implements Comando {
  private final Pedido p;

  public void executar() {
    p.alterarSituacao(
        EM_PRODUCAO);
  }
  public void desfazer() {
    p.alterarSituacao(PAGO);
  }
}

A fila guarda comandos

class FilaDeProducao {
  private Queue<Comando> fila;
  private Deque<Comando> feitos;

  void enfileirar(Comando c) {
    fila.add(c);
  }

  void executarProximo() {
    Comando c = fila.poll();
    c.executar();
    feitos.push(c);
  }

  void desfazerUltimo() {
    feitos.pop().desfazer();
  }
}

O que vira comando

EnviarParaProducao · RegistrarPagamento · RegistrarEntrega · CancelarPedido

Ganho

A fila guarda objetos, não chamadas: dá para respeitar a ordem (RNG23), desfazer (UC11) e registrar o histórico dos relatórios.

Cuidado

Uma classe por operação; e nem tudo é reversível — um hambúrguer já produzido não volta ao estoque.

Comportamental · escopo de objeto

State

Objetivo

Permitir que um objeto altere seu comportamento quando o seu estado interno muda. Para quem usa, é como se o objeto tivesse mudado de classe.

Contexto no Iron Burguer

O pedido percorre seis situações e cada uma permite operações diferentes: só se cancela antes da produção (RNG17) e só se entrega no Pronto, uma única vez (RNG25 e RNG26).

Problema

Um if por situação dentro de cada método (cancelar, produzir, entregar). A mesma regra fica repetida em vários pontos e basta esquecer um para o pedido ser entregue duas vezes.

Solução

Cada situação vira uma classe que implementa a interface SituacaoPedido. O Pedido delega a operação à situação atual, e cada situação sabe para qual outra pode transitar.

Recebido

Pago

Em produção

Pronto

Entregue

Cancelado: a partir de Recebido ou Pago (RNG17)

State no Iron Burguer

Sem o padrão

void entregar() {
  if (situacao == PRONTO) {
    situacao = ENTREGUE;
  } else if (situacao == ENTREGUE) {
    erro("MSG24");
  } else { erro("MSG16"); }
}
// e o mesmo if em cancelar(),
// produzir(), entregar()…

Cada situação é uma classe

interface SituacaoPedido {
  void cancelar(Pedido p);
  void entregar(Pedido p);
}

class Pronto implements SituacaoPedido {
  public void entregar(Pedido p) {
    p.setSituacao(new Entregue());
  }
  public void cancelar(Pedido p) {
    throw new RegraException("MSG16");
  }
}

O pedido delega

class Pedido {
  private SituacaoPedido situacao
      = new Recebido();

  public void entregar() {
    situacao.entregar(this);
  }
}

class Entregue implements SituacaoPedido {
  public void entregar(Pedido p) {
    throw new RegraException("MSG24");
  }
}

Ganho

A regra da entrega única fica em um só lugar: a classe Entregue sempre recusa. Fim da entrega em duplicidade (P9).

Custo

Seis classes de situação em vez de um atributo: vale a pena quando as regras por estado são muitas, como aqui.

Os quatro padrões no nosso projeto

Padrão Categoria e escopo Para que serve Onde entra no Iron Burguer Problema atacado
Prototype Criacional · objeto Cria objetos clonando um protótipo já configurado Lanches sugeridos do cardápio clonados no app (UC08) P5 — produção de pedidos errados
Singleton Criacional · objeto Garante instância única com ponto global de acesso Fila de produção e numeração da senha (UC13) P8 — a fila de entrega não é respeitada
Command Comportamental · objeto Encapsula a requisição como objeto, com desfazer e log Operações do pedido dentro da fila (UC11, UC13) P6 — a mudança no pedido é inviável
State Comportamental · objeto Muda o comportamento conforme o estado interno Situações do pedido e transições (UC11, UC15) P9 — a entrega do produto não é controlada

Conclusão

Juntos, os quatro contam o ciclo de vida de um pedido: ele nasce clonado de um lanche pronto, vira uma ordem numa fila única e muda de comportamento conforme a situação. Nenhum foi escolhido por ser famoso: cada um responde a um problema já registrado no DAN.
